## Full research

### TL;DR
- **Legally, forking and selling RoR is unambiguously permitted** — the code was published under GPLv3 from day one (Feb 8, 2009), inbound=outbound applies with no CLA, and the GPL expressly allows commercial sale. The binding legal constraints are narrower: the NVIDIA Cg Toolkit (non-free, must be *removed* not ported), the "Rigs of Rods" trademark/logo (must be renamed/re-skinned), and — the single biggest risk — the fact that virtually **all attractive vehicle/terrain content is community-made, unlicensed, and often carries real-world trademarks**, so a commercial fork must ship only its own licensed content.
- **Technically the port is feasible but non-trivial**: the true blocker is the NVIDIA Cg dependency (partly transitive through OgreTerrain on OGRE 1.11) plus the OGRE 14 upgrade. As of the 2026.01 release RoR still runs OGRE 1.11.6.1 and still requires Cg; an active maintainer PR (#3418, opened April 20, 2026) does the minimal OGRE 14.5 jump but *deliberately keeps Cg*. Input (OIS) and UI (MyGUI) are desktop-bound and need SDL + Dear ImGui work, but RoR is already roughly half-migrated to ImGui.
- **A curated fork that abandons mod compatibility escapes the great majority of the "impossible to port" problem.** Upstream is paralyzed almost entirely by ~15 years of community mods carrying Cg shaders; a fork shipping only its own GLSL-ES assets never inherits that constraint. **Recommendation: GO WITH CONDITIONS** — the conditions are hard content/trademark hygiene, full Cg removal, and a rename.

### Key Findings

**A1 — License provenance [LEGAL — RESOLVED in favor of GPLv3-from-start].** The primary source is decisive: Pierre-Michel Ricordel's own February 8, 2009 announcement on rigsofrods.blogspot.com states, "I decided to publish the source code of Rigs of Rods 0.36 under the GPLv3 licence." Secondary sources (Grokipedia; a Wikipedia summary) claiming "GPLv2 or later, later moved to v3" are **wrong** and contradict the primary source. The project's README confirms current licensing as GPLv3-or-later, and the copyright header reads "Copyright (c) 2005-2013 Pierre-Michel Ricordel / 2007-2013 Thomas Fischer / 2009-2025 Petr Ohlidal and Rigs of Rods contributors." There is **no CLA or DCO** evident; contributions are made under inbound=outbound GPLv3. Combined with the AUTHORS.md admission that the author list is incomplete and the SVN→Mercurial→Git migration, **relicensing or dual-licensing is realistically impossible** — you would need agreement from hundreds of unreconstructable contributors. This does not matter for forking (GPLv3 permits it outright) but permanently forecloses any closed-source or proprietary-relicensing plan.

**A2 — Non-free dependencies [Cg = BOTH; discord_rpc = LEGAL, minor].** The project's own BUILDING.md flags `nvidia-cg-toolkit` as "Not libre software." Cg is a proprietary NVIDIA product; NVIDIA's own Cg FAQ (developer.nvidia.com/cg-faq) states verbatim: "The Cg Toolkit is a legacy NVIDIA toolkit no longer under active development or support. Cg 3.1 is our last release and while we continue to make it available to developers, we do not recommend using it in new development projects because future hardware features may not be supported." The same page adds: "Going forward, we recommend new development with GLSL, or HLSL for Windows applications, rather than Cg." (Cg 3.1 dates to April 2012.) Shipping a GPLv3 binary that links Cg is a GPL compatibility problem: the GPL forbids linking against proprietary libraries unless the "system library" exception applies, and Cg is **not** a system library on Android (it is not part of the OS and does not even exist on ARM64/Android). **Cg must be removed, not ported** — it is both a legal blocker and a technical blocker. `discord_rpc` (Discord Rich Presence) is MIT-licensed and GPL-compatible, is optional, and is trivially removable; upstream already has a draft PR (#2908) to replace it. It is not a real obstacle.

**A3 — Addon library licenses [mostly LEGAL-clean].** These are all GPL-compatible free licenses:
- **Caelum** (sky): LGPL per the OGRE wiki; the OGRECave/RoR fork is tagged MIT. Consumed via RoR's own fork.
- **PagedGeometry** (vegetation): zlib/libpng ("Permission is granted to anyone to use this software for any purpose, including commercial applications"), originally by John Judnich, later maintained by Thomas Fischer (tdev). RoR maintains its own fork (RigsOfRods/ogre-pagedgeometry).
- **OGRE** itself: LGPL (older) / MIT (current) — GPL-compatible.
- **Hydrax** (water): historically LGPL; embedded as source in RoR including C++ shader string literals in `source/main/gfx/hydrax/MaterialManager.cpp`.
- **MyGUI, OIS, SocketW, AngelScript, fmt, RapidJSON, CURL, OpenSSL**: all permissive/LGPL and GPL-compatible.

None of the *code* libraries present an unstated-license redistribution risk. The redistribution risk is entirely in the **content**, not the libraries.

**A4 — Bundled content [THE PROJECT-KILLER — LEGAL].** This is the most dangerous area and the record is partly unclear. Confirmed facts: the README states the default install ships "only a small selection of built-in content," and that community vehicles/terrains "are separate from the core project and are not covered under the project's license, as they are contributed and licensed by their individual creators. As such, they will never be included with the game by default." The dedicated `RigsOfRods/content` repository (base content: `agora`, `dafsemi`, `simple2-terrain`) is GPL-3.0 licensed — so **only about three base assets are cleanly licensed.** A maintainer discussion on PR #2850 states the critical warning: aside from the ~3 GPL items in the content repo, "all else has no license what-so-ever... anybody can only download it and use in RoR... Also BTW some cars have textures with logos etc, which is not legal to use anyway or probably textures made from non-CC stuff." The forum repository explicitly warns "Resources listed here are not covered by the GNU GPL, unless indicated otherwise," and RoR's own docs note that most Google/YouTube-sourced car mods "contain models ripped from other games/websites, which goes against our Terms of Service." **Conclusion: a commercial fork cannot ship community content.** It must create or commission all its own vehicles, terrains, textures, audio, and fonts, and avoid real-world trademarks/trade dress, real-vehicle sampled audio, and real-world-derived terrain data. This is a content-production cost, not a code problem — but it is the item most likely to kill the project.

**A5 — Trademark [LEGAL, easily managed].** The RoR project publishes a Branding policy: "we take branding seriously and maintain a quality. Please do not edit, change, distort, recolor, or reconfigure the Rigs of Rods logo," with a defined logo set, typeface (Maven Pro), and color palette (RoR Blue #226699, RoR Red #882500, RoR Purple #3d0155). There is no evidence of a *registered* trademark, but the name and logo are claimed marks. A commercial fork **must not** use the "Rigs of Rods" name or logo — GPL governs the code, not the branding. A rename and new logo are required and are straightforward.

**A6 — Google Play distribution [LEGAL, manageable].** GPLv3 apps are distributable on Play (many exist), but two frictions apply. (1) **Source availability**: GPLv3 requires you to offer complete corresponding source to recipients; a public repo satisfies this. (2) **Anti-tivoization / installation information**: GPLv3 §6 requires that for "User Products" you provide the information needed to install modified versions. This is the genuinely thorny clause for a locked-down app; the practical mitigation used across the ecosystem is to distribute the APK such that a user can build and sideload their own modified version (Android permits sideloading), which satisfies the installation-information requirement without you signing their build. (3) **Repetitive-content / spam policy**: Google's current policy (Play Console Help, "Ensuring app quality," support.google.com/googleplay/android-developer/answer/13965279), under the "Repetitive content" heading, states verbatim: "We don't allow apps that spam users or Google Play, such as apps that send users unsolicited messages or apps that are repetitive." Google's related enforcement criteria specifically call out "Copying content from other apps without adding any original content or value" and "Creating multiple apps with highly similar content and user experience." A paid fork that adds substantial original value (new content, touch UI, mobile optimization) is defensible; a near-verbatim reupload of the free project is not.

**B1 — Cg surface area [TECHNICAL].** Cg appears in at least four shipped locations: `resources/caelum`, `resources/managed_materials` (PSSM shadows), `resources/materials` (e.g. `Nicemetal.cg`), and embedded C++ string literals in `source/main/gfx/hydrax/MaterialManager.cpp`. Upstream's own assessment (ohlidalp) is that RoR uses "almost none [of its own Cg shaders] except nicemetal.cg" — i.e., the *shipped* shaders are a small, tractable conversion job, and the dev team has already "pretty much agreed we can replace all shaders shipped with the game." Cg is essentially HLSL9, so `hlsl2glslfork` (BSD-licensed, used by Unity and OGRE for real-time Cg→GLSL/GLSL-ES conversion) is a viable migration path, though the tool is unmaintained since ~2016 and generates bloated code (mitigated by GLSL Optimizer). Modern alternatives: OGRE's own RTSS (runtime shader generation to GLSL/HLSL/Metal), or Microsoft's ShaderConductor (HLSL→SPIR-V→GLSL/ESSL/MSL via DXC + SPIRV-Cross). For a curated fork with a handful of its own shaders, hand-porting to GLSL ES 3.x is the cleanest route.

**B2 — OgreTerrain / transitive Cg [TECHNICAL — resolved by OGRE upgrade].** On OGRE 1.11 (RoR's current version), `TerrainMaterialGeneratorA` requires the Cg plugin to render terrain correctly — this is the transitive Cg dependency behind issue #1412. **This is fixed in modern OGRE.** Per OGRE's release notes (OGRECave/ogre Docs/13-Notes.md), verbatim: "Since 13.6, TerrainMaterialGeneratorA internally uses the RTSS to generate shaders." The underlying work was completed in OGRE 13.5 (released Oct 29, 2022: "The RTSS implementation of the Terrain shaders is now fully feature complete compared to the previous custom shader generator implementation"), and 13.6 shipped Jan 1, 2023. The RTSS emits GLSL/HLSL rather than Cg. Therefore **upgrading OGRE (to 13.6+/14) eliminates the transitive terrain-Cg dependency by itself** — the remaining Cg use is only the explicit shipped shaders (B1) and mod shaders (Part C).

**B3 — OGRE 14 migration status (as of mid-2026) [TECHNICAL].** RoR's stable 2026.01 release (Jan 3, 2026) **still uses OGRE 1.11.6.1 and still requires Cg** — confirmed by the master BUILDING.md dependency list and by RoR's own forum "Ogre Command Line Tools" resource ("built with Ogre version 1.11.6, the version used by the current stable release of RoR (2026.01)"). The 2026.01 release added gameplay/scripting features (tuning UI, gadgets, AngelScript IDE), not an engine upgrade. There is an active migration PR: **#3418, "Minimal viable OGRE upgrade to 14.5 (no RTSS, same old Cg, same old PSSM)," authored by lead maintainer ohlidalp, opened April 20, 2026, still open with ongoing CI activity as of mid-2026.** Its title reveals the strategy: a *minimal* jump to OGRE 14.5 (released Jan 10, 2026; current point release 14.5.2 dated Jan 31, 2026) that deliberately **keeps** Cg and old PSSM shadows and does **not** adopt RTSS in the first pass. A separate draft PR #3431 ("SDL," by contributor philocalyst, June 2026) addresses the OIS→SDL input migration. Upstream has described a "functional port" existing but blocked by performance problems (no geometry-batching solution causing "abysmal" performance on the Community Map) and Windows archive/Unicode issues requiring OGRE 1.13+'s MiniZ. **Implication for a fork: do not wait for upstream.** Upstream is intentionally preserving Cg/mod compatibility, which is exactly the constraint a fork should drop. A fork is better off migrating independently to OGRE 14.5 + RTSS and dropping Cg entirely.

**B4 — Desktop-only dependencies [TECHNICAL].** OIS (input) is keyboard/mouse/joystick-oriented and unsuitable for touch; upstream already drafted "Replacing OIS with SDL input" (PR #2983, 2022) and the new SDL PR #3431 (2026). SDL2/3 is the correct choice for Android and handles touch. For UI, **RoR is already substantially migrated to Dear ImGui**: the DearIMGUI integration is live (ported from OGRE 1.12's OgreImGuiOverlay), and PRs #1333/#1414/#2460 progressively replaced MyGUI. MyGUI still powers the main menu, settings, loaders, and the ".layout" dashboard HUD system, plus some internal string utilities. Realistic estimate: RoR is roughly half-migrated off MyGUI; a fork would finish the ImGui migration and add a bespoke touch UI (on-screen pedals/wheel/buttons), since (per the maintainers) RoR "was obviously never designed with touch controls in mind" and "UI elements are also quite small."

**B5 — Physics on mobile [TECHNICAL — favorable].** The Beam solver is a mass-spring-damper node/beam system: nodes carry mass and collide but are dimensionless; beams are massless spring+dampers. Forces are accumulated and applied in two phases per timestep (fixed Euler integration since 0.4.6, replacing the older unstable variable-timestep). Physics run on a background thread separate from rendering (the Actor/GfxActor split), with "selective parallelization" of force calculations; the powertrain sub-sim runs at up to 2 kHz (ohlidalp has noted 200–400 Hz may suffice). This is a CPU-bound float workload highly amenable to ARM64 with NEON SIMD. Winlator/Mobox (x86-emulation) benchmarks show high initial frame rates followed by thermal collapse — that collapse is largely the *emulation-translation overhead*, which native ARM64 eliminates. A realistic native budget on a mid-range phone is on the order of a single detailed vehicle (hundreds to low-thousands of nodes/beams) at playable rates, or several simple vehicles — comparable to what a low-end PC handled a decade ago. **Physics is not the blocker; graphics/asset fidelity and the Cg/OGRE stack are.**

**Part C — Strategic assessment [DECISIVE].** Upstream's own words locate the paralysis precisely: ohlidalp opened the "List of mods using legacy Cg shaders (risk analysis)" thread (Sep 12, 2023) stating "we pretty much agreed we can replace all shaders shipped with the game, we got stuck on the topic of shaders in mods." The problem is **not** "impossible to port" — it is "impossible to port WITHOUT BREAKING THE MOD ECOSYSTEM." A curated commercial fork that ships only its own licensed, GLSL-ES content gets to skip: (1) all mod Cg-shader compatibility (the entire upstream blocker); (2) backward compatibility with 15 years of legacy truckfiles/materials; (3) the transitive terrain-Cg problem (solved by OGRE 14 + RTSS anyway); (4) the "unlicensed community content" legal minefield. What it *loses* is enormous and must be honestly weighed: **the ~15-year library of thousands of high-quality community vehicles and terrains is the single biggest reason anyone plays RoR.** A fork with only its own content is a technically-impressive soft-body sandbox with a fraction of the content appeal. That is the core strategic tension: the fork gets to skip nearly all of upstream's technical paralysis, but pays for it by forfeiting the content that makes RoR worth playing.

### The Three Most Likely Project-Killers (ranked)

1. **Unlicensed / trademark-encumbered community content (A4).** Evidence: README + PR #2850 maintainer statement that all but ~3 base assets have "no license what-so-ever" and some carry real-world logos; docs note most third-party mods contain ripped models. A commercial product cannot ship these. This forces a fork to fund original content, and without the mod library the product loses its main draw.
2. **The Cg + OGRE 14 technical stack (A2/B1/B2/B3).** Evidence: BUILDING.md "Not libre software"; 2026.01 still on OGRE 1.11.6.1 + Cg; PR #3418 explicitly retains Cg. Removable, but it is the gating engineering effort and cannot be skipped for ARM64.
3. **GPLv3 permanence + trademark (A1/A5).** Evidence: the Feb 8, 2009 blogspot GPLv3 announcement; no CLA; the published branding policy. Not fatal, but it permanently forecloses closed-source monetization and forces a rename — shaping the entire business model.

### Recommendations

**Overall: GO WITH CONDITIONS.** The legal right to fork and sell is clear; the engineering is feasible; the physics suits mobile. The project succeeds or fails on content and Cg removal, not on legal permission.

**Stage 1 — De-risk before writing code.**
- Confirm the content strategy: commit to shipping **only** originally-created or properly-licensed (commissioned, CC-BY, or you-own-copyright) vehicles, terrains, audio, and fonts. Avoid all real-world marques, badges, trade dress, sampled real-vehicle audio, and real-world-derived heightmap/terrain data. *This is the make-or-break decision.*
- Choose a new product name and logo. Do not use "Rigs of Rods," its logo, or its color palette.
- Publish your fork's source repo from the first commit to satisfy GPLv3; plan for a user-sideloadable APK to satisfy §6 installation-information.

**Stage 2 — Technical spike.**
- Migrate independently to **OGRE 14.5 + RTSS** (do not wait for upstream PR #3418, which intentionally retains Cg). This alone kills the transitive terrain-Cg dependency.
- Port your handful of own shaders to **GLSL ES 3.x** by hand (they are few); reserve hlsl2glslfork/ShaderConductor only if needed.
- Replace OIS with **SDL2/3**; finish the MyGUI→Dear ImGui migration; build a touch control layer.
- Benchmark the Beam solver natively on ARM64/NEON with your own content to fix a realistic node/beam budget per device tier.

**Stage 3 — Product & compliance.**
- Add substantial original value (mobile UI, curated content, optimization) to clear Play's repetitive-content bar.
- Keep a clean CONTRIBUTORS/COPYING trail; you are permanently GPLv3.

**Benchmarks / thresholds that would change the recommendation:**
- If you **cannot** fund enough compelling original content → downgrade to **NO-GO** (you would be shipping an empty engine).
- If native ARM64 physics cannot sustain one detailed vehicle at ≥30 fps on a mid-range phone → reduce scope to simpler vehicles.
- If you intend any closed-source or proprietary-relicensed monetization → **NO-GO** (GPLv3 forbids it; relicensing is impossible here).
- If upstream merges a full RTSS/Cg-free OGRE 14 port → re-evaluate contributing upstream and maintaining a thin content/touch fork instead of a hard fork.

### Caveats
- **Not legal advice.** This is sourced research; neither the author nor the requester is a lawyer. Confirm content licensing, trademark, and GPLv3 §6 compliance with qualified counsel before commercial release.
- **A1 is now clear** (GPLv3 from Feb 8, 2009, per the primary blogspot announcement); the "GPLv2-first" claim in some secondary sources is contradicted by the primary source and should be disregarded.
- **A4 remains genuinely uncertain at the item level.** No canonical per-asset license manifest exists for RoR's bundled/community content beyond the ~3 GPL base assets in RigsOfRods/content. The safe operating assumption — supported by maintainer statements — is that community content is unlicensed and unusable commercially, but the exact status of each shipped default asset would require a file-by-file audit.
- **Forum sourcing.** The rigsofrods.org forum is behind an anti-bot wall ("Anubis"); maintainer quotes were captured via search-engine snippets that are consistent across queries and corroborated by GitHub, but the full threads could not be fetched directly.
- **PR #3418 internals** (discussion body) could not be fetched directly; its title, open state, author (ohlidalp), open date (Apr 20, 2026), and active CI status are confirmed from the live GitHub listing.
- Physics performance figures for native ARM64 are **estimates** extrapolated from the solver's architecture and emulation-layer behavior, not measured native benchmarks — no published native ARM64 RoR benchmark exists.
